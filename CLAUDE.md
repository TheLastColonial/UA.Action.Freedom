# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

UA.Action.Freedom — automation to support Ukrainian Action, a charity that runs supply convoys (donated vehicles + cargo) from the UK to Ukraine. The domain models the lifecycle of preparing a convoy: sourcing vehicles, packing boxes of items, crewing each vehicle for both legs of the journey, building a manifest per vehicle, and tracking the convoy's route and status through to delivery.

## Commands

Built on .NET 10 (`net10.0`), solution file is `UA.Action.Freedom.slnx`.

```
dotnet build UA.Action.Freedom.slnx                                  # build everything
dotnet test --solution UA.Action.Freedom.slnx                        # run all test projects
dotnet test --project tests/UA.Action.Freedom.Tests.Unit/UA.Action.Freedom.Tests.Unit.csproj   # run one test project
dotnet test --project <proj> --filter-query "/*/*/ClassName/MethodName"                         # run a single test
dotnet run --project src/UA.Action.Freedom.Api/UA.Action.Freedom.Api.csproj          # run the API alone (http://localhost:5100)

cd iac/local && cp .env.example .env && docker compose up -d --wait   # local Azure simulation: substrate + db schema (db-deploy)
cd iac/tofu  && tofu init && tofu apply                              # ...then its resources + database logins
cd ../local && docker compose up db-seed                             # (optional) load fictional dev data; re-runnable
curl http://localhost:8080/health/ready                              # all Healthy == wired up correctly
```

`dotnet test` runs in **Microsoft.Testing.Platform (MTP) mode**, opted in via `global.json`
(`{ "test": { "runner": "Microsoft.Testing.Platform" } }`) because the .NET 10 SDK dropped the
legacy VSTest bridge that `xunit.v3` relied on. MTP mode changes the CLI: pass the solution as
`--solution` and a project as `--project` (bare paths are no longer positional). Filter with
xUnit v3's MTP options — `--filter-class "*Name"`, `--filter-method "*Name"`,
`--filter-namespace`, `--filter-trait "k=v"`, or `--filter-query "/asm/ns/class/method"`
(the [query filter language](https://xunit.net/docs/query-filter-language)) — **not** the plain
`--filter` / `FullyQualifiedName~...` VSTest syntax, which silently matches nothing here.
`--configuration`, `--no-build`, `--no-restore`, `--verbosity` still work as before.

Test framework is xUnit v3 with `AwesomeAssertions` (fluent assertions), `NSubstitute` (mocking), and `MELT` (testable `ILogger`). `Xunit` is globally usable via implicit `<Using>` in each test csproj — no `using Xunit;` needed.

The solution builds clean, with **zero warnings** — the Domain `CS8618` nullability warnings were cleared by the domain remediation (`required` on genuinely required scalars, nullable navigation properties). Keep it at zero: a warning that is allowed to persist is one nobody reads.

## Working in parallel (agents)

Several agents may work on this repo at once. Each gets **its own git worktree and its own full local stack**; nothing is shared but the object database. Full guide: `docs/parallel-agents.md`; checklist skill: `.claude/skills/agent-worktree`.

```
pwsh scripts/agent/agent.ps1 new <name> -Up     # (bash: scripts/agent/agent.sh new <name> --up)
cd ../UA.Action.Freedom.worktrees/<name>        # work ONLY here
. ./.agent/env.ps1                              # (bash: . ./.agent/env.sh) before Integration/BDD/Playwright
pwsh scripts/agent/agent.ps1 list|status|ports|db|down [-Volumes]
pwsh scripts/agent/agent.ps1 remove <name>      # from the main checkout, once the PR is merged
```

- **Slots.** The main checkout is slot 0 and keeps the default ports (8080/8081/1433/...). Agent N (1-9) gets `20000 + N*100 + offset` for every published port (edge +0, Keycloak +3, SQL +9, Azurite +10..12, Vite +13), its own compose project/containers (`freedom-<name>-*`), image tags (`:<name>`), volumes and tofu state. The slot registry is `<main .git>/agent-slots.json`.
- **Tear down with `agent.ps1 down [-Volumes]`**, not raw `docker compose down -v`: the script also clears the tofu state that a volume wipe would otherwise leave stale.
- **Do not** run bare `docker compose`, `tofu apply` or infrastructure-backed tests against ports you did not claim, edit another worktree, or edit the generated files (`iac/local/.env`, `iac/tofu/terraform.tfvars`, `.agent/`, `.devcontainer/agent/`). A worktree's `iac/local/.env` is generated from the main checkout's, so secrets change there.
- **Hot reload.** `agent.ps1 up` layers `iac/local/docker-compose.dev.yml`: `app`, `customs-worker`, `manifest-worker` run `dotnet watch` on the bind-mounted source (no image rebuild), and the operator UI runs on Vite at `http://localhost:<VITE_PORT>/app/`. Schema changes: `agent.ps1 db`. Provisioning: `up` re-runs `tofu apply`. `up -NoHotReload` runs the baked images as CI does — do that before a PR that touches a Dockerfile or project references.
- **Compose parameters** (defaults reproduce the old behaviour; the only intentional default change is a 4 GB SQL Server cap and Keycloak's own heap default now being explicit): `COMPOSE_PROJECT_NAME`, `FREEDOM_PREFIX` (container name prefix), `FREEDOM_IMAGE_TAG`, every `*_PORT`, `VITE_PORT`, `KEYCLOAK_JAVA_HEAP`, `MSSQL_MEMORY_LIMIT_MB`. A new compose service must use `${FREEDOM_PREFIX:-freedom}-<svc>` for `container_name`, a `${..._PORT:-default}` host port, and a `${FREEDOM_IMAGE_TAG:-local}` tag, or it will collide between agents. Any new host-port-dependent URL goes in `scripts/agent/Agent.Lib.ps1` (`New-AgentTfVars`/`Get-AgentTestVariables`) too. The SPA's Keycloak authority is a Dockerfile build arg (`VITE_OIDC_AUTHORITY`) fed from `KEYCLOAK_PORT`.
- **Memory.** Agent stacks are capped (Keycloak heap, SQL limit) to ~3.5 GB each; main + two uncapped stacks exhausted a 16 GB Docker VM and made `dotnet watch` crash with `Cannot allocate memory`. `up` warns when the VM cannot fit another stack. If services restart in a loop, check `docker run --rm alpine free -m` before debugging code.
- The slot/port/env logic is Pester-tested: `Invoke-Pester scripts/agent/tests` (Pester 5+). Change it test-first.
- The dev container (`.devcontainer/`, experimental) is for editing/building/testing; run the stack from the host.

## Architecture

Solution follows a layered structure under `src/`:

- **`UA.Action.Freedom.Domain`** — plain C# domain model, no framework dependencies. This is where the business concepts live (see below).
- **`UA.Action.Freedom.Application`** — use cases / orchestration. Hand-rolled CQRS: `Abstractions/ICommandHandler<,>` + `IQueryHandler<,>`, one handler per use case, all registered explicitly in `AddFreedomApplication()` (no MediatR, no assembly scanning). Slices so far: `Vehicles/`, `People/`, `Convoys/`, `Receivers/`, `Boxes/`, `Manifests/`, `Locations/`, `Categories/`, `Donations/`, `Declarations/` — each with create/update/delete commands and get/list queries behind its own `I*Repository` port. Convoys has two ports, split along the table boundary: `IConvoyRepository` (the journey — dates, route, publication, arrival) and `IConvoyVehicleRepository` (the truck list, `dbo.ConvoyVehicle`, and the crew, insurance, cargo and ferry booking hanging off it). Handlers return small outcome enums (`Created`/`Conflict`, `Updated`/`NotFound`) so the API maps status codes without exceptions; where creation cannot conflict the handler returns the new identifier instead (`People` mints a `Guid`, `Convoys` returns the `IDENTITY` the insert assigned). Each slice's `*ReadModel` is a flat read + write shape whose CLR types line up with the column types — a deliberate CQRS projection, not a workaround: `Domain` is hydratable since the remediation, but Dapper maps rows, not object graphs. Paging is clamped in the list handler (1..200, default 50), never in the endpoint.
- **`UA.Action.Freedom.Data`** — persistence. `SqlConnectionFactory` (`IDbConnectionFactory`) builds `SqlConnection`s from `ConnectionStrings:Freedom`, same key as the health check. One Dapper repository per slice — `Vehicles/`, `People/`, `Convoys/` (two: `ConvoyRepository` for the journey and `ConvoyVehicleRepository` for the truck list, its crew, its insurance, its cargo and its ferry booking), `Receivers/`, `Boxes/`, `Manifests/`, `Locations/`, `Categories/`, `Donations/` (two: `DonorRepository` for the split identity and `DonationRepository` for the drop-offs and the donor report), `Declarations/` (`DeclarationRepository` — one conditional `UPDATE` per transition, VINs via `SqlKey.Of`) — all registered by `AddFreedomData()`. **There are two connection factories, and the difference is a security boundary.** `IDbConnectionFactory` → `ConnectionStrings:Freedom`, the application's own identity (`freedom_app`), which is `DENY SELECT`'d on the `sensitive` schema. `ISensitiveDbConnectionFactory` → `ConnectionStrings:FreedomSensitive`, a principal in the `ground_officer` role, and the only way to read a Ukrainian delivery address. `ReceiverDetailRepository` is the one class that takes the second — a separate interface rather than a named lookup, so a repository asking for the ordinary factory *cannot* be handed the Ground Officer connection, and widening that needs a constructor change a reviewer will see. **Dapper's constructor-mapping is strict**: `dbo.Vehicle` uses `int` (not `tinyint`/`smallint`) for the enum and year columns so they line up with the CLR types of `VehicleReadModel`'s primary constructor, and the same rule governs every new table. Transactions are held only where one fact spans several rows, each scoped to one aggregate: `ConvoyRepository.ReplaceRouteAsync` (a route is meaningful only as a whole journey, and it is a **merge**: ids survive, survivors are parked on negative sequences while they move, removed points are deleted), `ConvoyLeaderRepository.NominateAsync` (closes the open assignment and opens the next), `ConvoyRepository.DeleteAsync` (the truck list goes before the convoy, because `FK_ConvoyVehicle_Convoy` is NO ACTION; the crew and the insurance cascade from the entry, and **both statements sit inside the `catch`** — the refusal from a manifest comes from the *first* of them), `ConvoyVehicleRepository.AssignCrewAsync` / `UnassignCrewAsync` (removing a driver takes them off the vehicle's insurance in the same transaction, and recording the insurance names every current driver), `ConvoyVehicleRepository.AllocateBoxAsync` (a box is on at most one truck-list entry; the entry, the box and the existing allocation are read under lock and the allocation inserted or moved in one transaction), `ConvoyRepository.ArriveAsync` (the arrival stamp and the handover are one fact; it takes the convoy row first and never scans `dbo.Vehicle` under a lock — it deadlocked against inspection updates until it stopped), `PersonRepository.AddAsync` / `DeleteAsync` (identity and personal data arrive together; erasure checks, deletes the detail, then removes or stamps the identity), `ReceiverDetailRepository.ResolveAsync` (the audit row is written in the same transaction as the read),, `BoxRepository.IssueQrCodeAsync` / `AssignBayAsync`, and `ItemCategoryRepository.SetCodeAsync` (the mapping row and the stamp on its category). **VINs and manifest references are `varchar(32)` keys: pass them with `SqlKey.Of(...)` (or `CAST(@x AS varchar(32))` when a record is the parameter object).** Dapper sends strings as `nvarchar`, and under the SQL collation that converts the *column*, so an unmarked `WHERE Vin = @vin` scans and locks the whole table. A delete refused by a foreign key is caught (`SqlErrors.ForeignKeyViolation`) and returned as `DeleteResult.StillReferenced` → 409, never a 500. The schema lives in **`database/UA.Action.Freedom.Database`**, an SDK-style SQL project (`Microsoft.Build.Sql`, in the `.slnx`) built into a dacpac: one plain `CREATE` per table plus the `sensitive` schema, the roles and their `GRANT`/`DENY`s — the end state only, **no migration code** (no guards, no `ALTER ... ADD`, no data moves; every stack is rebuilt from scratch). SqlPackage diffs it against the target and generates the change. Locally the `db-deploy` compose one-shot publishes it (`database/Dockerfile` + `database/deploy.sh`), and an optional `db-seed` service (run separately via `docker compose up db-seed`) loads fictional dev data from `database/seed/dev-seed.sql` — re-runnable, guards against re-seeding an already-populated database. It ships on its own `Database` workflow as an OCI artifact, separately from code. **Principals are the environment's, not the dacpac's**: `iac/local/sql/principals.sql`, applied by `iac/tofu/database.tf`, creates the `freedom_app`/`freedom_sensitive` logins and users and adds them to roles, and the publish passes `ExcludeObjectTypes=Users;Logins;RoleMembership` so it never touches them. Write CHECK constraints in SQL Server's normalised form (`>= 0 AND <= 3`, not `BETWEEN`) or every publish recreates them — the `Database` workflow fails when a re-publish is not a no-op. No EF, no DbUp.
- **`UA.Action.Freedom.Api`** — ASP.NET Core minimal API host (`Program.cs`). `/vehicles` CRUD (`Vehicles/VehicleEndpoints.cs`, `MapFreedomVehicles()`) — natural key on VIN, so the route is `/vehicles/{vin}`, plus `PUT /vehicles/{vin}/inspection` (the servicing result, `vehicles:service`). `/people` CRUD (`MapFreedomPeople()`), server-minted `Guid` key, `?driversOnly=true` for the dispatcher's shortlist. `/convoys` CRUD (`MapFreedomConvoys()`) plus its sub-resources: `PUT/GET /convoys/{id}/route` (**merged by `routePointId`**, renumbered 1..n in list order; a point has a name, a kind of `Stop`/`Overnight`/`Border`/`Hub` and, for a `Border` only, a customs authority; the PUT answers `200` with the points and their ids, `422` for an id not on the route, `409 route-point-in-use` when `IRoutePointReferences` says something refers to a removed point), `GET|PUT /convoys/{id}/leader` (the **Convoy Leader**: `dbo.ConvoyLeaderAssignment`, one open row per convoy and the history kept, a Driver crewed on the convoy, `convoys:lead-assign` = Administrator/Dispatcher; `IConvoyLeaderRepository` is its port, and removing the sitting leader from the crew is `409 convoy-leader-on-crew`), `GET /convoys/{id}/vehicles` (the truck list, withdrawn vehicles included), `PUT /convoys/{id}/vehicles/{vin}`, `DELETE /convoys/{id}/vehicles/{vin}?reason=` (before publication a removal, afterwards a **withdrawal** — the entry, crew, insurance and manifest all stay), `GET|PUT|DELETE /convoys/{id}/vehicles/{vin}/crew/{personId}` (vehicle crew — an optional `{ "role": "Driver"|"Passenger" }` body, default Driver; one seat per person per convoy; Dispatcher-only for write), `POST /convoys/{id}/vehicles/{vin}/manifest` (**opens the manifest** — there is no `POST /manifests`), `GET|PUT|DELETE /convoys/{id}/vehicles/{vin}/boxes/{boxId}` (**cargo is a box allocated to the truck-list entry** [ADR 0004]: `PUT` on a second vehicle *moves* the box, `boxes:write`; `GET /convoys/{id}/vehicles/{vin}/boxes` is `boxes:read`; refused 409 while the vehicle is withdrawn or its manifest's GMR exists, which is transitional until plan 15), `GET|PUT|DELETE /convoys/{id}/vehicles/{vin}/ferry` (the vehicle's **outbound** booking, P1: operator, reference, sailing, ticket details, optional cost; `convoys:write`), `GET|PUT|DELETE /convoys/{id}/vehicles/{vin}/insurance` (per vehicle per convoy, names the drivers it covers: removing one keeps it in cover, adding one leaves them uncovered until it is recorded again; required to depart; `convoys:write`), `GET /convoys/{id}/readiness` (advisory: one driver required, two advised, insurance naming every driver), `POST /convoys/{id}/arrive` (once every vehicle still travelling has a Delivered/Lost/Returned manifest; hands Delivered/Lost vehicles over for good), and `POST /convoys/{id}/publish-truck-list`. `PUT /people/{id}/login` (`people:write`, so Administrator only) links the login a volunteer signs in with — the token subject, stored on the erasable `PersonDetail.IdentitySubject` behind a filtered unique index; 204/404/409 subject-in-use — and `GET /me` (any authenticated caller) reports the caller's subject, roles and, once linked, person id and display name. **Who did it always comes from `ICurrentPerson`** (`Application/Abstractions`; `Api/Configuration/ClaimsCurrentPerson` resolves the subject through `IPersonRepository.FindBySubjectAsync`, scoped and memoised): box validation, bay placement, insurance (`RecordedByPersonId`, FK to `dbo.Person`) and the receiver access log (`PersonId`, no FK, no subject) are signed as the caller's linked volunteer, and a login nobody has linked is refused with `403` / problem type `login-not-linked` by `LoginNotLinked.RequireAsync` before any handler runs — no "unknown" identity is ever written, and the box bodies no longer carry a person id (an extra one is ignored). `DELETE /people/{id}` is an **erasure** (below), and removes the login link with the rest of the personal data. `/receivers` CRUD (`MapFreedomReceivers()`) returning reference/organisation/region/**status** only, plus `PUT /receivers/{ref}/status` and `GET /receivers/{ref}/usage` (**Administrator only**, `receivers:register` — registration is an act of authorisation, so the Ground Officer who writes a receiver cannot grant it; the usage read lists the box and live-convoy *identifiers* a status change touches, never an address), plus `GET|PUT /receivers/{ref}/detail` for the delivery address — Ground Officer alone, and every resolve is audited. `/boxes` CRUD (`MapFreedomBoxes()`) plus `GET|POST|DELETE /boxes/{id}/items` (an item names its **category** and may carry a quantity, a `valueGbp` with its `valueSource` of `Donor` or `Estimate`, an `expiresOn` and a `commodityCode` of its own; `POST` answers `200` with `{ itemId, warnings }`, and a not-carried, expired or short-dated item is accepted and warned about; reads add `categoryNameEn`, `isNotCarried` and `shelfLife` worked out in `ListBoxItemsHandler`, never stored), `POST /boxes/{id}/validate` (refused `409 box-has-expired-items` while an item past its `expiresOn` is in the box), `POST /boxes/{id}/replace` (**an attested box is replaced, never edited or deleted** — see *Boxes are replaced, and the label lists the contents* below), the QR-code lifecycle (`POST|GET|DELETE /boxes/{id}/qr-code`, `GET /boxes/{id}/qr-code/image`, `GET /boxes/{id}/label`, `GET /boxes/scan/{token}`), and bay allocation (`PUT|GET|DELETE /boxes/{id}/bay`, `GET /boxes/{id}/bay/history`). `/manifests` (`MapFreedomManifests()`) — read, `PUT` (notes only; the convoy and the vehicle are its identity) and delete, but **no `POST`**: one is opened on its truck-list entry. Plus `GET /manifests/{id}/crew` (a read of the convoy's crew), `GET /manifests/{id}/boxes` (a read through the vehicle's allocations; `PUT`/`DELETE /manifests/{id}/boxes/{boxId}` answer **410 Gone** and point at the vehicle route until plan 15 removes them), `GET /manifests/{id}/weight`, `GET /manifests/{id}/elo` and `GET /manifests/{id}/elo/document` (the French logistics envelope and its barcode, read-only and read back from blob storage — **there is no `POST`**, an envelope is requested by filing the vehicle's ELO declaration), `POST /manifests/{id}/document` (the travelling document, requested once the load is signed off), the old `/manifests/{id}/ens*` routes (**410 Gone** until plan 15), and **`/convoys/{id}/vehicles/{vin}/declarations`** (the vehicle's GMR, ENS, ELO and goods lists — `GET`, `POST {kind}/record`, `POST {kind}/refused`, `POST {gmr|elo}/file`, `GET|PUT|DELETE ens`, `GET ens/filing-sheet`; see *Declarations are one concept per vehicle* below), and one `POST` per edge of the state diagram (`propose`, `approve`, `reject`, `prepare`, `ready`, `depart`, `deliver`, `lose`, `return`). `/categories` (`Categories/CategoryEndpoints.cs`, `MapFreedomCategories()`) — `GET|POST /categories`, `GET|PUT /categories/{id}` and `PUT /categories/{id}/codes/{UK|EU|UA}` (a `null` code clears the mapping): the fixed list of item categories each with a hazard class, sensitive and not-carried flags, a `WarnWithinDays` shelf-life window and a customs code per authority; `IsFixed` is written only by the seed. `/donors` and `/donations` (`Donations/DonationEndpoints.cs`, `MapFreedomDonations()`): donors are a split identity (`dbo.Donor` the anonymous key, `dbo.DonorDetail` the erasable details, `dbo.DonorDisplay` the one place "Former donor" is decided), `DELETE /donors/{id}` is an erasure that is **never refused** and stamps `ErasedAt` when a donation still names the donor, `GET /donors/{id}/report` is built only from what a donor may be told (no receiver, region, route or address — the type has nowhere to carry one), and a box item may name its `donationId`; policies `donations:read` (all operational), `donations:write` (Administrator/Dispatcher/Loader, O22) and `donors:erase` (**Administrator only**). `/locations` CRUD (`Locations/LocationEndpoints.cs`, `MapFreedomLocations()`) plus its bays (`GET|POST /locations/{id}/bays`, `PUT|DELETE /locations/{id}/bays/{bayId}`) — where a `Box` is physically shelved once it reaches a depot. JWT bearer auth (`Configuration/AuthenticationExtensions.cs`, `AddFreedomAuthentication`/`AddFreedomAuthorization`) driven by `OidcOptions`: `RoleClaimType = "roles"`, `MapInboundClaims = false` (Keycloak/Entra send a flat `roles` claim — without this it gets rewritten to the WS-Fed role URI and every policy fails), `RequireHttpsMetadata` off in Development, audience checked only when `Oidc:Audience` is set (Keycloak issues `aud: account`). Policies: `vehicles:read` (Administrator/Purchaser/Dispatcher/Loader/Mechanic), `people:read` / `convoys:read` (Administrator/Purchaser/Dispatcher/Loader), `vehicles:write` (Administrator/Purchaser/Mechanic), `vehicles:service` (Administrator/Mechanic — recording the inspection that decides whether a vehicle may join a convoy; a Purchaser can edit a vehicle but not pass it), `people:write` (Administrator only — approving volunteers is the Administrator's job), `convoys:write` (Administrator/Dispatcher), `convoys:assign-drivers` (Dispatcher only — day-to-day convoy crewing), `convoys:lead-assign` (Administrator/Dispatcher — nominating or reassigning the Convoy Leader; a leader is a fact, not yet a login capability), `receivers:read` (all operational **plus** GroundOfficer), `receivers:write` (Administrator/GroundOfficer), `receivers:register` (**Administrator only**), and `receivers:detail` (**GroundOfficer alone** — the narrowest policy in the API; deleting a receiver also sits behind it, because that removes an address), `boxes:read` (all operational), `boxes:write` (Administrator/Dispatcher/Loader), `boxes:validate` (Administrator/Loader — packing a box and vouching for what is in it are different acts) and `boxes:allocate-bay` (Loader only — shelving a box is a warehouse act, not a packing one), `manifests:read` (all operational), `manifests:write` (Administrator/Dispatcher) and `manifests:approve` (**Administrator only** — approval signs off the load and freezes the manifest, so the person who builds one is not the person who signs it off; it files nothing), `manifests:declare` (Administrator/Dispatcher — recording, refusing, withdrawing and filing a vehicle's declarations; deliberately **not** GroundOfficer even though a Ground Officer is who files it, because that isolation runs both ways), `locations:read` (all operational) and `locations:write` (**Administrator only** — depots and bays are infrastructure, not day-to-day box handling), `categories:read` (all operational) and `categories:write` (**Administrator only** — the category-to-customs-code mapping decides what is declared at a border, O31). GroundOfficer is excluded from every other policy, and the isolation runs both ways. Mechanic is in the three vehicle policies and nothing else. Request bodies validated by FluentValidation via `Configuration/ValidationFilter<T>`; errors are `ProblemDetails` (`AddProblemDetails()` + `UseExceptionHandler()`). Also real configuration (`Configuration/`, environment-variable only), `/health/live` + `/health/ready` probes that genuinely check SQL, blob, both work queues, the ICS2 declaration store and OIDC discovery (`Health/`), and data-protection keys persisted to blob storage. OpenTelemetry traces, metrics and logs are wired by `builder.AddFreedomApiTelemetry()` (`Installer/TelemetryInstaller.cs`), which adds ASP.NET Core and SQL instrumentation to the shared `UA.Action.Freedom.Telemetry` setup (below); health probes are excluded from tracing (`Filter`) and from HTTP metrics (`DisableHttpMetrics()`). The exception handler's 400/500 bodies carry the `traceId`. Exported over OTLP to whatever `OTEL_EXPORTER_OTLP_ENDPOINT` names (the Grafana OTEL-LGTM container locally, App Insights in Azure); the exporter is skipped when that variable is unset, so `dotnet run` and the in-memory component tests collect but do not ship. References `FluentValidation` for future use.
- **`UA.Action.Freedom.CustomsWorker`** — the Azure Function of the C4 diagram, as a plain `BackgroundService` so it runs anywhere. It serves **two border authorities** on three loops driven by `CustomsWorkerService`: `GmrSubmissionProcessor` drains `customs-work` and submits to HMRC; `EloEnvelopeProcessor` drains `elo-envelopes` and creates French logistics envelopes; `GmrOutcomeCollector` polls the Push Pull Notifications box for outcomes (pull only — no inbound endpoint, per `recommendations.md` §4.1) and writes GMR documents to blob storage. Separate queues rather than one with a message type, so a French refusal cannot stall a UK submission behind it and each gets its own poison queue. Storage and queue access sit behind ports (`ICustomsWorkQueue`, `IEloWorkQueue`, `IGmrDocumentStore`, `IEloDocumentStore`) so the rules about *when a queue message is deleted* — the part that loses a convoy's paperwork if wrong — are unit-testable without a storage account. **The ELO side has one disposition rule the GMR side does not: nothing is dead-lettered once French customs has accepted an envelope.** Creating one is not idempotent and the `numeroDossier` exists only in that response, so a barcode that is absent or not base64 is stored as an envelope without one, and a failed store leaves the message (accepting that the retry makes a second envelope — visible and recoverable, where losing the first is not). `EloTokenProvider` is a singleton holding the OAuth2 password-grant token for its whole lifetime, as §2.2.5.1 of the service contract asks; with no `Elo:TokenEndpoint` configured it returns `Elo:StaticToken`, which is how the WireMock-backed local stack works. `GvmsApiException`/`PushPullNotificationsApiException`/`EloApiException` all carry the response body in their message: the worker logs status, type and (for ELO) the bounded `FONC-ERR-00x` code only, never the exception object or `libelleErreur`, which quotes the declaration it objected to.
- **`UA.Action.Freedom.ManifestWorker`** — renders the document that travels with a vehicle. `ManifestDocumentProcessor` drains the `manifest-documents` queue and writes to the `manifests/` blob prefix, with the same three-way queue disposition as the Customs Worker (complete / dead-letter / leave alone). **It has no database access at all**, and that is the design: the Freedom Application composes the whole document and puts it on the queue, so the worker cannot read a Ukrainian delivery address because it cannot read anything. `ManifestDocumentRequest` has nowhere to carry a street, contact or phone — the redaction is the type, not a rule someone has to remember (see the data-sensitivity note below). Output is plain text on purpose: deterministic and testable, and a PDF with letterhead can wrap it later without changing what is on it.

- **`UA.Action.Freedom.Telemetry`** — the one OpenTelemetry setup all three services share (`AddFreedomTelemetry()`): resource, `AddSource/AddMeter("UA.Action.Freedom.*")`, `Azure.Storage.*` spans, HttpClient/runtime instrumentation, the OTLP exporter, and `RedactingActivityProcessor` (route not path, no query, client URLs reduced to the peer, SQL on the `sensitive` schema blanked — it must stay registered *before* the exporter). It also holds the queue layer: `QueueTelemetry` (producer/consumer spans; the producer writes `traceparent` into the JSON body and the worker's span *links* to it), `QueueFlowMetrics`, `QueueDepthReporter` (work and poison depth/age, sampled on a timer) and `WorkerLoopMetrics` (per-loop heartbeat). **Never set `service.namespace`** — it changes the Prometheus `job` label every dashboard filters on. **Never make a person, receiver, plate, VIN, manifest reference or HMRC response a metric tag, span attribute or log field**; tags are bounded sets (handler, outcome enum, `ManifestStatus`, fixed reasons). Business metrics live beside the code they count, on BCL `Meter`s with no OpenTelemetry dependency: `FreedomMetrics` (Application — every `ICommandHandler` is wrapped by `InstrumentedCommandHandler` at the end of `AddFreedomApplication`, so put the success case *first* in each outcome enum), `CustomsMetrics`, `ManifestWorkerMetrics`, `DbErrors` (Data). Each takes/has an `Unobserved` instance so existing positional constructions keep working. Dashboards are `iac/local/grafana/dashboards/*.json`; the metric catalogue is `iac/local/grafana/README.md`; the gotchas are in `docs/gotchas-and-open-questions.md` § Observability.

- **`HMRC.GVMS`** (`src/HMRC.GVMS`) / **`HMRC.PushPullNotifications`** (`src/HMRC.PushPullNotifications`) — NSwag-generated typed HTTP clients for the HMRC Goods Vehicle Movements and Push Pull Notifications APIs. These are standalone HMRC SDKs and deliberately carry no `UA.Action.Freedom` prefix — namespace and assembly name match the project name. The `Generated/` folder is committed codegen output; regenerate with `build/nswag/regenerate.ps1 -Api <goods-vehicle-movements|push-pull-notifications>` and see `build/nswag/README.md`. Each project adds a hand-written `*ClientOptions` + `Add*Client(this IServiceCollection)` DI extension (typed `HttpClient`, HMRC versioned `Accept` header, caller supplies the OAuth handler). Do not hand-edit `Generated/`. Their unit tests live in `tests/HMRC.GVMS.Tests.Unit` and `tests/HMRC.PushPullNotifications.Tests.Unit` — one dedicated test project per SDK, not folded into `UA.Action.Freedom.Tests.Unit`.

- **`EDI.ELO`** (`src/EDI.ELO`) — the same NSwag-generated-client-plus-DI-wrapper shape as the HMRC SDKs, for the French customs ELO (*Enveloppe Logistique Obligatoire*) EDI API used to pair customs declarations with a physical crossing. Also carries no `UA.Action.Freedom` prefix. Two structural differences from the HMRC SDKs: (1) `EloClientOptions.BaseUrl` has no default — the spec declares no `servers:` entry, so `AddEloClient` requires a `configure` callback and throws if it doesn't set a base URL; (2) the spec has no security scheme at all — `Authorization`, `messageCode`, `functionalId`, `messageId`, `correlationId` are plain required header *parameters* on each of the three operations (create/modify/retrieve an envelope), so the caller passes them as ordinary method arguments on every call rather than via a chained `AddHttpMessageHandler`. Regenerate with `build/nswag/regenerate.ps1 -Api elo` — **`-Raw` is no longer required and now warns**: `build/nswag/elo.preprocess.json` carries three corrections this API needs, and `-Raw` skips all of them. `preserveHeaderParameters` keeps `Authorization` from being stripped as a transport header (the original reason for the `-Raw` rule); `overrideProperties` rewrites the `pdf` field, which the spec declares as `enum: [formatbytebase64]` and whose generated string-enum converter **threw on every successful response that carried a barcode** — the same defect class as the PPNS bug below, but blocking; and `keepComponents` stops the unreferenced `ENV_NOT01` notification DTO being pruned. The barcode is `string?` base64 in both `Enveloppe.Pdf` and `ENV_CRE02.Pdf`, because the spec's schema and its examples disagree about which — read whichever is non-null. Its unit tests live in `tests/EDI.ELO.Tests.Unit`. Consumed by `CustomsWorker` (below).

  > **Known bug: `HMRC.PushPullNotifications` cannot deserialise a notification.** HMRC sends `"messageContentType": "application/json"`; NSwag generated the enum with `[EnumMember(Value = "application/json")]` but decorated the property with `JsonStringEnumConverter<MessageContentType>`, which matches C# member names (`Application_json`) and ignores `[EnumMember]`. Every response throws `JsonException`. This affects real HMRC, not just the local stub, so do not "fix" it by changing the stub. The fix belongs in `build/nswag/` plus a regeneration. Reproduce with the local environment — `iac/README.md` § Known issues.

Seven test projects under `tests/`. `HMRC.GVMS.Tests.Unit` and `HMRC.PushPullNotifications.Tests.Unit` hold the SDK client tests. The four `UA.Action.Freedom.Tests.*` projects each cover every slice the same way, so adding one means adding a file in each:

- **`Unit`** — handler tests with NSubstitute against the slice's `I*Repository` port, plus both workers' processors. A `*TestData` factory per slice with every parameter defaulted; a fresh substitute per test, no shared fixture.
- **`Component`** — the API in memory via `WebApplicationFactory<Program>`, with an `InMemory*Repository` and the `TestAuthHandler` scheme swapped in by a `FreedomApi.With*(...)` helper. **A fake must enforce every rule its SQL does** (keys, conditional `WHERE`s, clean-up on delete) — `InMemoryConvoyRepository` once returned `[]` where the SQL returned `null` and kept crews the SQL deleted, so tests passed against behaviour production did not have. Assertions read `JsonElement`, never the read model, so the JSON contract is what is pinned. This is where the authorization split for each slice is proved.
- **`Integration`** — the real Dapper repositories against real SQL, `[Trait("Category","Integration")]`, `ConnectOrSkipAsync` probing the *table* through the shared `SqlTestDatabase` helper, which connects as `freedom_app` (never `sa` — sysadmin bypasses the grants the app actually holds) and calls `Assert.Skip` when the table is not there — or fails instead when `FREEDOM_REQUIRE_INTEGRATION=true`, which CI's acceptance job sets because it has just stood the stack up. **The assembly is `[assembly: Parallelization(Mode = ParallelMode.None)]`** — these share one database and the foreign keys between Vehicle, Convoy and Manifest made parallel classes deadlock each other about one run in four. Do not re-enable it.
- **`BDD`** — **Reqnroll** (`Reqnroll.xunit.v3`), one `.feature` per slice driving HTTP against the **deployed containers** (edge on `http://localhost:8080`, Keycloak on `http://localhost:8081`, overridable by `FREEDOM_*` env vars) with real password-grant tokens. `Background` calls `Given the Freedom API exposes "/route"`, which `Assert.SkipUnless`es the feature and distinguishes "the stack is down" from "the running image predates this feature". Generic HTTP steps live in `ApiSteps`; Reqnroll matches step text globally, so a duplicate in a per-slice class is an ambiguous binding, not an override. After a code change, rebuild the image (`cd iac/local && docker compose build app manifest-worker && docker compose up -d --wait app edge manifest-worker`) before running it.

**CI:** `.github/workflows/build-and-test.yml` runs on `push`/`pull_request` to `main` **only when a code path changes** — a `paths:` filter of `src/`, `tests/`, `database/`, `iac/`, `web/`, `build/`, the root `UA.Action.Freedom.slnx`/`global.json`/`GitVersion.yml`, or the workflow file. Doc-only commits (`docs/**`, `plans/**`, `*.md`) do not trigger it; `workflow_dispatch` forces a run. It has five jobs. `build-and-test` runs `dotnet test --solution` (Integration + BDD self-skip there — no infrastructure) and emits the version outputs. `frontend` runs the `web/` gates (typecheck/lint/format/test/build). `acceptance` stands up the `iac/` simulation (`docker compose` substrate + `tofu apply` for realm/storage/schema), **builds the three service container images** (`ua-action-freedom-{api,customs-worker,manifest-worker}`) plus the `db-deploy` image that publishes the schema, runs Integration + BDD + Playwright against *those exact images*, and on a non-PR run pushes them to `ghcr.io/thelastcolonial/*` (`<semver>`/`-beta.<run>`, `sha-<short>`, `latest` on main) with build-provenance attestations — building here rather than in a separate job is what makes the tested image the published one. `nuget` packs and pushes **only** `HMRC.GVMS` + `HMRC.PushPullNotifications` to GitHub Packages (`-beta.<run>` on non-fork PRs, full on main). `release` (main push + `isRelease` only) cuts a GitHub Release annotated with the pushed image digests — no file assets. `nuget` and `release` gate behind `acceptance`, so a failing e2e blocks both. `iac/local/docker-compose.yml` is unchanged; CI runs it with `--no-build` because the images are pre-built and loaded. **`.github/workflows/database.yml`** is the database's own pipeline (`database/**` paths): builds the dacpac (`DacVersion` from GitVersion), publishes it to an empty SQL Server service container, fails if a `DeployReport` of a second publish shows any operation, and on a non-PR run `oras push`es it to `ghcr.io/thelastcolonial/ua-action-freedom-database` with a provenance attestation.

### Domain model (`src/UA.Action.Freedom.Domain`)

Core entities and how they relate:

- **`Person`** — base type for any individual (name, DOB, join date, phone). `Driver : Person` adds `Convoys` and `Committed`. `Receiver` (the delivery contact) carries an `Organisation`, a region, and — for a Ground Officer only — an `Address` and a responsible `Person`.
- **`Vehicle`** — a donated vehicle (VIN, plate, weight, fuel/transmission type, purchaser, drivers, and its `Convoy`). It records a `ValueGbp` with a `ValueSource` of `Purchased` (the price paid) or `Estimate` (a donated one), both or neither (O11, O33). Vehicles are themselves part of the aid — they are handed over in Ukraine, not driven back.
- **`Convoy`** — a group of `Vehicle`s travelling together, with a `Route` (ordered list of `Address` stops) and start/expected-end timestamps. `ArrivedAt` marks the journey over: Delivered/Lost vehicles are then handed over (`Vehicle.HandedOverAt`, never offered again).
- **`ConvoyVehicle`** — **the truck list, and the single statement of "this vehicle is travelling with this convoy"** (`dbo.ConvoyVehicle`, keyed `(ConvoyId, Vin)`). The crew, the insurance and the `Manifest` all hang off it. There is no `Vehicle.ConvoyId`: a pointer could hold only the current convoy and had to be cleared at arrival, so an arrived convoy lost its own truck list. Withdrawal is a stamp (`WithdrawnAt`, `WithdrawnReason`), not a delete — a vehicle that breaks down leaves the convoy and may join a later one, but its manifest still describes a real load.
- **Vehicle crew** — `CrewRole` (`Driver` | `Passenger`) per person per vehicle per convoy, one seat per person per convoy (`UQ_ConvoyVehicleCrew_Convoy_Person`); there are no journey legs ([ADR 0007](docs/adr/0007-journey-legs-are-removed-from-the-crew-model.md)). This is the only crew record in the system; the manifest reads it. **`VehicleInsurance`** — per vehicle per convoy, naming the drivers it covers (`dbo.ConvoyVehicleInsuranceDriver`; a crew driver with no row there is *uncovered*), required to depart (`VehicleInsurance.InCover` and `CoversAllDrivers` are the one statement of the rule; `VoidedAt` is an explicit void, no crew change sets it). Readiness (one driver required and two advised per vehicle, insurance naming every driver, a route; withdrawn vehicles skipped) is advisory, in `ConvoyReadiness.Assess`.
- **`Box`** — a packed container of `Item`s with a confirmed weight, validation state (`ValidatedBy`/`ValidatedAt`), current `Location`, and target `Receiver`. A validated box is **voided** (`VoidedAt`) and replaced by a new box that names it (`ReplacesBoxId`); a voided box counts in nothing.
- **`Donor`** / **`Donation`** — a donor is an anonymous key (`DonorId`) plus erasable `DonorDetail` (name, email, phone), the same split as `Person`/`PersonDetail` and never the same record as a volunteer; a `Donation` is one donor's drop-off and `BoxItem.DonationId` (nullable, for items that predate donations) attributes each item to it. The `dbo.Donation` foreign key to `dbo.Donor` has no cascade, so erasing a donor keeps the donation, its items and its value.
- **`Item`** / **`ItemCategory`** — an `Item` names a category (`CategoryId`) and may carry a quantity, a value in pounds with its `ValueSource` (`Donor` or `Estimate`; no currency is converted, D5), an `ExpiresOn` date and a `CommodityCode` of its own, which wins over its category's. `ItemCategory` (ADR 0014) carries the names (`NameUk` starts empty), `IsFixed` (written only by the seed), `HazardClass`, `IsSensitive`, `IsNotCarried` (D21) and a `ShelfLifeRule` (`WarnWithinDays`, **unverified, D25 — data an Administrator changes, never a constant**), plus a customs code per `CustomsAuthority` (UK, EU, UA) in `dbo.CategoryCustomsCode`. `ShelfLife.Assess` says `Expired` once the date has passed (needs no category), `Short` within the window, otherwise `Fine`. The open-ended rest stays in `dbo.BoxItem.PropertiesJson`, string values only, read through `BoxRepository`'s private `BoxItemRow` seam (a non-string value there is kept as its raw JSON text rather than refused); the typed fields are columns. An item is declared on the ENS filing sheet under its own code, else the **EU code of its category**, and a gap names the category. A box holding an expired item is refused validation. The fixed categories live in `database/seed/dev-seed.sql`, **not** in the dacpac (gotchas §9 Q18).
- **`Declaration`** — a statement to a customs authority about one vehicle's load: kind (`Gmr`, `Ens`, `Elo`, `GoodsList`), scope `(ConvoyId, Vin, ReceiverRef?)`, status, reference and bounded reason code, on one lifecycle (`DeclarationTransitions`). Replaces the GMR stamp, the ELO blob and the ENS blob as the statement of "what has been declared"; `Manifest.GmrSubmittedAt` remains only the freeze signal until plan 15. See *Declarations are one concept per vehicle* below.
- **`Manifest`** — the **document pack for one `ConvoyVehicle`**: its border weight, its GMR and its ELO, with delivery notes. It carries no crew, no cargo and no ferry booking of its own: its cargo is the boxes allocated to the same truck-list entry (`dbo.ConvoyVehicleBoxAllocation`, `BoxAllocations` in Domain, keyed on `BoxId`) and its ferry booking is `dbo.ConvoyVehicleFerryBooking`. `(ConvoyId, Vin)` is `NOT NULL` and a composite foreign key to the truck-list entry, unique per pair — the two used to be independent nullable columns, so nothing checked the vehicle was on that convoy and one vehicle could carry two manifests. `ManifestWeight.Total` sums vehicle + cargo + a fixed 200kg (2 drivers + bags) + 45kg fuel allowance — this constant-padding convention is intentional (border-check estimate), not a bug, and it lives in **one** place now rather than the three it was copied into.
- **`Location`** / **`Bay`** — a distribution hub and the 1m×1m storage areas within it. A `Bay.Code` is unique only within its own `Location`, not globally. **`BoxBayAssignment`** records a box being placed in a bay (who, when); vacated rows are kept, not deleted, so a box's shelving history survives it moving on. **`BoxQrCode`** is the issue/revoke-shaped label a Loader scans to find a box again. See `docs/domain/key-concepts.md` § Location / § Bay for the full shape — these were added by the Locations-and-Box-Allocations feature and are covered there in more depth than here.

`DriverTeam`/`DriverTeamId` are gone: a manifest no longer keeps its own primary/secondary pairs, and the primary/secondary distinction went with them — nothing used it, and readiness counts drivers.

`Person`'s "is a driver" question is modelled by subtyping (`Driver : Person`), not a flag — so the Domain project has no `IsDriver` boolean and no way to express `Committed` on a plain `Person`. The `IsDriver` boolean and its "`Committed` requires `IsDriver`" validation rule (`docs/gotchas-and-open-questions.md` §4) live one layer up, on the flat CQRS shape (`Application/People/PersonReadModel.cs`, `Api/People/PersonRequestValidators.cs`) — that's where to look for it, not here.

**Spelling conventions:** the misspelled type names have all been corrected — `Veichle` → `Vehicle`, `Reciever` → `Receiver`, `Person.Joinned` → `Joined`, `ResponsibleIndiviual` → `ResponsibleIndividual`. Nothing is half-applied any more; keep it that way, and finish any future rename across the whole solution in one go.

**Identity is deliberately not standardised.** Each entity carries the id type that matches how it is actually referenced: `Vehicle` has no id (VIN is the natural key and the route segment), `ConvoyId(int)`, `BoxId(int)`, `ManifestId(string)`, `PersonId(Guid)`, `ReceiverRef(Guid)`, `LocationId(int)`, `BayId(int)`, `BoxBayAssignmentId(int)`, and `Item` a raw `Guid`. The two `Guid`s are not enumerable on purpose — they identify volunteer personal data and Ukrainian receivers. Do not "harmonise" these.

**`ManifestStatus` is the 10-state model the code implements today**, which `docs/recommendations.md` §5.3 asked to be confirmed as authoritative. `docs/manifest-status.puml` now draws the **target** three-state load sign-off ([ADR 0004](docs/adr/0004-the-manifest-is-the-load-sign-off.md)); the ten-state diagram the code matches is in git history at `f659eed`, and [plan 15](docs/plans/15-manifest-signoff-lifecycle.md) brings the code into line. The old 6-state `record` with instance properties is gone. The edges live as data in `ManifestTransitions.CanTransition(from, to)` (`Manifest.cs`), pinned edge-by-edge by `tests/UA.Action.Freedom.Tests.Unit/Domain/ManifestTransitionsTests.cs`. The happy path is linear; the only backward edge is `Rejected → Proposed`. Nothing may reopen a confirmed manifest, because confirmation is what releases it to GMR submission — and once `Manifest.GmrSubmittedAt` is set the manifest is frozen entirely (§5.2).

### Target hosting architecture (Azure)

Not yet provisioned on Azure, but **simulated locally in `iac/`** — see `iac/README.md`. `docker compose up -d --wait` starts stand-ins for every container on the diagram (Traefik for Cloudflare, Azurite for Blob/Queue Storage, SQL Server for Azure SQL, Keycloak for Entra External ID, WireMock for the HMRC APIs, Grafana OTEL-LGTM for App Insights, Mailpit for ACS); `tofu apply` then provisions resources into them the way `azurerm` would. Use it before changing anything here — several of the gotchas below are exercised by it.

The local Keycloak realm (`iac/tofu/keycloak.tf`) seeds **three** logins, all with password `password`: `admin` (Administrator), `operator` (Dispatcher + Loader + Mechanic + Purchaser), and `groundofficer` (GroundOfficer). Locally each app role is delegated through a Keycloak **group** of the same name and users get roles by group membership — this is the group-assignment model Entra keeps behind a paid tier, used here only because it keeps the seed logins readable; the token still carries a flat `roles` claim, so authorisation policies port to Azure app roles unchanged. `groundofficer` is deliberately kept as its own isolated login so the receiver-address segregation that role carries in production holds locally too — no other seed user can resolve a receiver address. Keycloak runs with `KC_HOSTNAME_BACKCHANNEL_DYNAMIC: "true"` (`iac/local/docker-compose.yml`) so the discovery document's `jwks_uri`/`token_endpoint` follow the request host: the app container fetches signing keys over the compose network (`keycloak:8080`) while the token `iss` stays the browser-facing `localhost:8081`. Without it, in-container token validation fails because the app is told to fetch keys from a `localhost` URL it cannot reach.

The full reasoning, cost model and security posture live in **`docs/recommendations.md`**; read it before making infrastructure or hosting changes, because most of these choices are load-bearing rather than incidental.

The binding constraints:

- **Permanent Azure free allowances only.** No trial credits, no introductory offers. Anything with a fixed monthly charge is out — this is why the design uses Cloudflare Free at the edge rather than Azure Front Door.
- **Convoys run roughly once a month**, so load is long quiet periods punctuated by a burst of a few days. Everything scales to zero between convoys, and cold starts are an accepted trade.
- **UK South**, for UK data residency over volunteer and donor personal data.

Decisions already taken:

| Concern | Choice |
| --- | --- |
| Web UI + API | **One deployable** on Azure Container Apps (Consumption). Do not split them without a reason — the split doubles compute and adds an auth boundary. |
| Background work | Azure Functions (Consumption), queue- and timer-triggered |
| Database | Azure SQL free offer (serverless, auto-pause) |
| Documents | One Blob Storage account, `manifests/` `gmr/` `elo/` prefixes — not one account per document type |
| Identity | Microsoft Entra External ID, app roles (not group assignment, which needs a paid tier). The local Keycloak sim does use role groups — a readability convenience, not a design change; see above. |
| Edge | Cloudflare Free — DNS, TLS, CDN, WAF |
| CI/CD | GitHub Actions → ghcr.io, authenticated by OIDC federated credential |

Two gotchas that will cost you a debugging session if missed:

- **Persist ASP.NET Core data-protection keys** to Blob Storage, encrypted with a Key Vault key. Container Apps replicas are ephemeral, so the default in-container key ring silently logs users out after every scale-to-zero. See `docs/recommendations.md` §3.2.
- **The Azure SQL free offer's auto-pause delay has a 60-minute minimum**, so scattered short bursts of activity burn the monthly compute allowance far faster than their duration suggests. See §2.3.

Security principles this design commits to: managed identity everywhere (shared-key auth *disabled* on storage, Entra-only auth on SQL), pull-based HMRC integration rather than an inbound webhook, short-lived user-delegation SAS for documents, and segregated storage for Ukrainian delivery detail. That last one matters most — see the note under Docs below.

### Where the domain is going: target design and implementation plans

Product discovery (October 2026) redesigned large parts of the domain, recorded in **ADRs 0004–0017**. **None of it is built yet.** The code is the *current* system; `docs/domain/` describes the *intended* one. When the two disagree, the domain documents are the direction of travel: do not "fix" a domain document to match the code, and do not quietly build around a rule — raise it.

- **Business rules** are in `docs/domain/`: `convoy-operations.md`, `boxes-and-donations.md`, `customs-declarations.md` (rules only, every rule linked to its decision). **Every decision, with its rationale, open questions and the amendments still due, is in `docs/domain/decisions.md`** — IDs `D`, `P`, `X`, `O` (for example `decisions.md#x6`), never reused.
- **The headline changes**: journey legs are removed (one crew seat per person per convoy); the manifest becomes only the Administrator's **load sign-off**, and any later load change sends it back for re-approval; boxes are allocated to the truck-list entry; GMR, ENS, ELO and the Ukrainian goods list become one per-vehicle **Declaration** whose staleness is derived from a snapshot; **filing is manual by default**; readiness becomes blocking requirements with **no override**, and departure is one convoy action; a **Convoy Leader** role, scoped to one convoy, with time-limited and audited access to destination addresses; Receiver registration status; donors as an erasable split identity; item categories mapped to customs codes and GBP values; attested boxes are **replaced, never edited**, with a bilingual label; every entity records who last changed it.
- **Implementation is a series of 19 plans** in `docs/plans/` — one branch and one PR each, merged by the developer before the next starts. `docs/plans/README.md` holds the index, the dependency graph, the owner gates (plans 16, 17 and 19 stop for sign-off before code) and the **agent execution protocol**. When implementing any of these ADRs, work from the matching plan and follow that protocol.

**A Receiver has a registration status, and only `Registered` can be named ([ADR 0012](docs/adr/0012-receiver-registration-gates-convoys-and-boxes.md)).** `dbo.Receiver.[Status]` is 0 pending, 1 registered, 2 suspended, 3 expired (`Domain.ReceiverStatus`, CHECK `>= 0 AND <= 3`); a new receiver is pending, and **only `SetStatusAsync` writes it** (the `INSERT` and `UPDATE` leave it out, so an ordinary edit cannot register one). `ReceiverEligibilityCheck` is the one check behind every place a receiver is named: a box's destination (`CreateBoxHandler`/`UpdateBoxHandler` — a bad reference is `422 receiver-not-found`, an unregistered one `409 receiver-not-registered`, and a box already pointing at a since-suspended receiver can still be *moved*, because only a *new* allocation is gated) and a vehicle's **handover receiver** (`dbo.ConvoyVehicle.HandoverReceiverRef`, `PUT /convoys/{id}/vehicles/{vin}/handover-receiver`, `convoys:write`, refused once the convoy has arrived or the vehicle has been withdrawn). **Departure does not check the handover receiver yet — plan 13.** A hub is `dbo.Location.IsRegisteredHub`, set under `locations:write` (Administrator) with no status of its own (D36). `DELETE /receivers` still sits behind `receivers:detail` (it removes an address), and now also fails on a foreign key if a box or a vehicle still names the receiver.

**Every entity records who last changed it, and when ([ADR 0017](docs/adr/0017-every-entity-records-its-last-change.md)).** Entity tables carry `LastChangedBy` (FK to `dbo.Person`, no cascade, nullable) and `LastChangedAt`, and every `INSERT`/`UPDATE` in a Dapper repository sets both **in the same statement** from `@changedBy`, which `ChangeStamp.With(attribution, ...)` adds to the parameters. Where the caller comes from is deliberate: repositories take `IChangeAttribution` (`Application/Abstractions`), a scoped holder that `ChangeAttributionMiddleware` (`Api/Configuration/ChangeAttribution.cs`, after `UseAuthorization`) fills from `ICurrentPerson` for every `POST`/`PUT`/`PATCH`/`DELETE` — so no handler or command carries a person id, nothing a client sends can set it, and a statement cannot forget it. **An unlinked login is refused `403 login-not-linked` on every write**, with two exceptions marked `.AllowUnlinkedLogin()`: `POST /people` and `PUT /people/{id}/login`, which are how a login becomes linked (those changes are stamped with a time and no person — `LastChangedBy` NULL is "nobody linked", never an invented identity). Every read model that has the pair exposes `LastChangedByName`/`LastChangedAt`, read through `ChangeStamp.ReadColumns/ReadJoin` and **`dbo.PersonDisplay`**, the one place "Former volunteer" is decided (an erased volunteer's `PersonDetail` is gone, so the LEFT JOIN yields it; the crew list reads its names from the same view). **Exempt tables** are links and logs that already say who (`Person`, `ManifestBox`, `ConvoyVehicleInsuranceDriver`, `ConvoyVehicleInsurance`, `BoxBayAssignment`, `ReceiverDetailAccessLog`), listed with their reason in `tests/UA.Action.Freedom.Tests.Integration/Schema/LastChangedGuardTests.cs` — **a new table without both columns fails that test**, which reads the catalogue as `freedom_sensitive` because `freedom_app`'s `DENY` on `sensitive` hides those tables from it. The component fakes mirror all of it through `IRecordsWhoChanged`/`ChangeLedger` (`FreedomApi` attaches the request's attribution); a test that wants an unlinked caller supplies its own roster. Because most people are now named by *some* row, `PersonRepository.DeleteAsync` stamps `ErasedAt` far more often than it deletes the identity.

**Volunteers are a split identity, so they can be erased.** `dbo.Person` is only the anonymous key (`Id`, `CreatedAt`, `ErasedAt`) that crews and box records point at; the personal data is in `dbo.PersonDetail`, cascading from it. `DELETE /people/{id}` deletes the detail row — a real delete, for UK data protection — and removes the identity too unless a past record names it, in which case it is stamped `ErasedAt` and those records read "Former volunteer". It is refused (409) while the person is crewing a convoy that has not arrived, or a vehicle whose load is not yet delivered, lost or returned. Both are now questions of the one crew record, where they used to be asked of two unconnected tables. Reads come from `dbo.PersonDetail` alone, so an erased person is "not found" everywhere without anyone filtering. Do not put personal data back on `dbo.Person`.

**The receiver segregation is built and enforced — do not weaken it.** Three independent controls, and each one holds if the others are removed by mistake:

1. **The `receivers:detail` policy** — GroundOfficer alone (`Configuration/AuthenticationExtensions.cs`).
2. **A separate database identity** — `ISensitiveDbConnectionFactory` / `ConnectionStrings:FreedomSensitive`, used only by `ReceiverDetailRepository`.
3. **`DENY SELECT ON SCHEMA::sensitive TO freedom_app`** — the application's own identity physically cannot read a delivery address. `tests/UA.Action.Freedom.Tests.Integration/Receivers/ReceiverSegregationTests.cs` asserts this against the real database, and it only means anything because the app connects as `freedom_app` rather than `sa` (sysadmin bypasses permission checks — that switch is why `iac/local/.env.example` carries `FREEDOM_APP_DB_PASSWORD`).

`ReceiverReadModel` has no address or contact fields at all (only the `Status` and the `LastChangedByName`/`LastChangedAt` pair every read model carries — the status says only that the receiver may be sent to, **never what kind of body it is: do not add a field that does, decision D33**), so code holding one has nothing sensitive to leak — that is what makes redaction structural in document generation and logging rather than a rule someone has to remember. `ReceiverDetailRepository.ResolveAsync` writes the audit row *in the same transaction* as the read, and logs the attempt even when nothing is found; the trail outlives the address it describes.

**The manifest lifecycle, and what "frozen" actually means.** Every state change is its own `POST` (one per edge of the as-built ten-state model; `manifest-status.puml` now shows the target), never a `PATCH` of a status field: most pairs of states are unconnected, and two of the rules have nothing to do with the pair involved. `TransitionManifestHandler` delegates legality to `ManifestTransitions.CanTransition` and adds the two rules the diagram cannot express — a manifest may only be **proposed** against a convoy whose truck list is published (`process.puml`), and a frozen manifest may not be **reopened**.

Note the precision on the freeze: §5.2 forbids *edits*, not *progress*. `Manifest.GmrSubmittedAt` blocks `PUT`, team assignment, cargo changes and delete — but `Preparing → Ready → InTransit → Delivered` still run, because those report what happened to a load HMRC already knows about. Blocking them would strand every approved manifest in `Confirmed` for ever. Only `Proposed`/`Rejected` are refused when frozen, and that is a guard against a future backward edge rather than a path anything takes today.

**Approval signs off the load and files nothing; filing is a separate, manual-by-default act on the vehicle's declarations ([ADR 0004](docs/adr/0004-the-manifest-is-the-load-sign-off.md), [ADR 0005](docs/adr/0005-declarations-are-per-vehicle-with-derived-staleness.md), [ADR 0006](docs/adr/0006-filing-is-manual-by-default.md)).** `POST /manifests/{id}/approve` runs `ApproveManifestHandler`, which does one thing: `ConfirmAndFreezeAsync` sets status and the GMR stamp in **one** statement (a manifest that is Confirmed but not yet frozen is editable, and that window is the thing §5.2 rules out). It no longer needs an ENS, enqueues nothing and hands nothing off; `GmrSubmittedAt` stays the freeze signal until plan 15. The travelling document is requested explicitly with `POST /manifests/{id}/document` (`RequestManifestDocumentHandler`, `manifests:write`, `409` until the manifest is frozen) — composed in the Application so the Manifest Worker needs no database. The GMR and the **French logistics envelope** (ELO) are filed from `/convoys/{id}/vehicles/{vin}/declarations/{gmr|elo}/file` by `FileDeclarationHandler`, **only where that authority's `SubmissionMode` is `Automatic`** (`Customs__GmrSubmissionMode`, `Customs__EloSubmissionMode`, default `Manual`; `DeclarationSubmissionModes`, bound in `Program.cs`); in manual mode the route is `409` and says to record the reference instead. `HandOff(kind, ...)` still counts a partial failure (`FreedomMetrics.ApproveFailedAfterFreeze`, stage `gmr`/`elo`/`document` — the name predates the move) and logs the exception *type* before rethrowing. **The message goes first and the declaration is stamped `Filed` second**, so a failed enqueue leaves it unfiled and retryable; and because the workers have no database, **automatic `Filed` means *enqueued*, not *accepted***. The envelope carries only a crossing profile (`EloCrossingProfile.HumanitarianAidToUkraine`: `IMPORT`, `PLEIN`, TIR/ATA, no transport contract — French Customs' own guidance for this traffic, which under ENV_CTR_RG08 reduces the requirement to a single ENS) and a declaration identifier, which is **the `Reference` of the vehicle's `Accepted` ENS declaration**. See `docs/schemas/edi/onboarding.md`, `docs/adr/0002-elo-envelope-on-manifest-approval.md` and `docs/gotchas-and-open-questions.md` §5a.

**Declarations are one concept per vehicle (`dbo.Declaration`, `Application/Declarations/`).** Kind `Gmr|Ens|Elo|GoodsList`, scope `(ConvoyId, Vin, ReceiverRef?)` — the receiver is for a goods list only (one per receiver per vehicle per convoy) — a foreign key to the truck-list entry, and one lifecycle held as data in `DeclarationTransitions` (`Draft → ReadyToFile → Filed → Accepted | Refused`, `Refused → Draft`, `Filed|Accepted → Stale → Withdrawn → Draft`, `Accepted → Closed`), pinned edge by edge in `DeclarationTransitionsTests`. **`Stale` is set only by derived staleness (plan 09) and `Closed` only by a crossing (plan 18); plan 08 defines both and never takes them.** A filtered unique index allows one declaration per scope and kind that is not `Withdrawn`; a withdrawn one is kept as history. **A reference is write-once**: `RecordReferenceAsync` is one conditional `UPDATE ... WHERE Reference IS NULL OR Status = Refused`, so the database settles a race (a refused declaration may be recorded afresh; an automatic `Filed` with no reference may later have one recorded). **A refusal keeps a bounded reason code only** (`DeclarationRefusalReasons.Codes`) — the authority's free text can quote the declaration, so the validator rejects anything else and nothing stores it. An ENS records straight to `Accepted` (an MRN exists only on acceptance). **An ELO is refused (`409`) until the vehicle has an accepted ENS**, on record and on file alike. Routes: `GET .../declarations`, `POST .../{gmr|elo|goods-list}/record`, `POST .../{kind}/refused`, `POST .../{gmr|elo}/file`, and the ENS's own `GET|PUT|DELETE .../declarations/ens` plus `GET .../ens/filing-sheet`; reads are `manifests:read`, every act `manifests:declare`. The old `/manifests/{id}/ens*` routes answer **410** until plan 15. `FK_Declaration_ConvoyVehicle` is NO ACTION, so a convoy or vehicle with declarations is refused deletion (`409`); the two `dbo.Person` foreign keys are indexed because every erasure checks them and an unindexed one scans under lock (a BDD deadlock).

**Declaration staleness is derived from a snapshot of the load, never set (plan 09, [ADR 0005](docs/adr/0005-declarations-are-per-vehicle-with-derived-staleness.md)).** `Domain/LoadSnapshot.cs` holds `LoadSnapshot` (version, VIN, withdrawn flag, per box its id, weight, Receiver, whether that Receiver is registered, and per item its category, quantity, value and code) and the pure `Staleness.IsStale(snapshot, current)`, whose rows mirror the table in `docs/domain/customs-declarations.md` (pinned in `StalenessTests`). The snapshot is stored on `dbo.Declaration` (`SnapshotJson` + `SnapshotVersion`, both or neither, no names/addresses/contacts) by `POST .../declarations/{gmr|elo|goods-list|ens}/ready` (`MarkReadyAsync`: Draft or ReadyToFile to ReadyToFile, creating the draft if none; `?receiverRef=` for a goods list), or, for a declaration recorded straight to filed, by `DeclarationSnapshots.StampAsync` after the record or file succeeds (`StoreSnapshotAsync` writes only where there is none, so the first load stands; a refused declaration recorded afresh has its snapshot cleared by the same `UPDATE` and is re-stamped). The current load is composed by `VehicleLoadReader` from the existing ports (truck-list entry, `ListBoxesAsync`, `IBoxRepository`, `IReceiverRepository`), fresh on every read, not cached. `ListDeclarationsHandler` reports `Stale` **in place of** `Filed` or `Accepted` when the snapshot differs (`DeclarationStaleness.Derive`); **the database is never written on read**, so the row still says Filed/Accepted until it is withdrawn, and the ENS/ELO gating (`EnsAccepted`) still reads the stored status. `SnapshotJson`/`SnapshotVersion` on `DeclarationReadModel` are `[JsonIgnore]`: they never reach the API. A snapshot is compared on the fields its `Version` has (`Staleness.Fingerprint`), so a later field does not make every filed declaration stale; unknown JSON properties are ignored. `GET /convoys/{id}/tasks` (`manifests:read`; the SPA shows it to `manifests:declare`) lists a re-declare task per stale declaration with a `resolution` per kind (`RedeclareResolution`) and carries identifiers only; `POST .../declarations/{declarationId}/withdraw` (`manifests:declare`, `409` unless currently stale) runs `WithdrawAndRedraftAsync`: Filed|Accepted to Stale to Withdrawn and a new Draft for the same scope in one transaction, keeping the record and its reference (for the ENS this is the plan 08 supersede). **"Declarations current" does not block departure yet; plan 13 makes it a blocking requirement.** The component fakes need `FreedomApi.WithManifests(boxes:, receivers:)` to give the load reader something to read.

**A convoy has a budget, costs and per-vehicle equipment, none of which gates departure (plan 12; O12, O13, O37).** `dbo.ConvoyBudgetLine` (one planned amount per `CostType`: Fuel, Ferry, Hotel, Insurance, Other), `dbo.ConvoyCost` (money **entered**), `dbo.EquipmentItem` (the catalogue) and `dbo.ConvoyVehicleEquipment` (hangs off the truck-list entry like the ferry booking). They have their own ports, `IConvoyBudgetRepository` and `IVehicleEquipmentRepository`, their own Dapper classes (`ConvoyBudgetRepository`, `VehicleEquipmentRepository`) and their own endpoint classes (`BudgetEndpoints`, `EquipmentEndpoints`), so the convoy repositories are untouched; routes are in the README. **Only `Fuel` and `Other` are ever entered**, and the table CHECK says so: a ferry, hotel or insurance cost lives on its booking or policy and `BudgetPosition` (`Application/Convoys/BudgetUseCases.cs`) *reads* it, so it is never counted twice (a booking is counted even if its insurance is voided: the money was spent). Hotel has nothing to read until plan 11. **Equipment counts under `Other`** (not a sixth cost type) and `equipmentGbp` shows it on its own; a line costs its recorded cost, else quantity x the catalogue's unit cost (`VehicleEquipment.CountedCostGbp`). Equipment lives in tables the value-delivered calculation never reads, which `VehicleEquipmentRepositoryTests` pins. `Budget.Compare` is pure; a type with no line is shown but never "over", while a line budgeted at 0 is over as soon as anything is spent. `GET /convoys/{id}/readiness` carries `advisories` ("No budget set", "Fuel is over budget") that never change `ready`. Fuel is entered by the Dispatcher until plan 18 gives it to the Convoy Leader. In the SPA, the budget and equipment "steps" are the **Budget** and **Equipment** tabs of the convoy page (the create flow already lands on the tabs, so there is nothing to block or skip).

**The ICS2 declaration is recorded, not submitted.** An ENS is the EU's pre-arrival safety-and-security declaration; **the ELO cannot be created without its MRN**, so the order is ENS → MRN → ELO → barcode → check-in with no catching up at the border. Freedom does not talk to ICS2: the Shared Trader Interface speaks EU eDelivery **AS4** (ebMS3/SOAP, an eIDAS sealing certificate registered in UUM&DS, a mandatory conformance run), which needs the always-on *inbound* endpoint `recommendations.md` §4.1 declines — so **the NSwag-generated-client pattern behind `EDI.ELO` and the HMRC SDKs does not transfer, and there is no `src/ICS2.*` project and no queue.** A Ground Officer files in the EU Customs Trader Portal and a Dispatcher records the MRN (`PUT /convoys/{id}/vehicles/{vin}/declarations/ens`, `manifests:declare`); `IEnsDeclarationStore` is the seam an IT Service Provider's adapter would drop into. Three consequences worth knowing before touching this slice. **Approval is no longer gated on the ENS; the ELO is** (`FileDeclarationOutcome.EnsNotAccepted` / `RecordDeclarationOutcome.EnsNotAccepted` → 409, nothing written). **A recorded MRN is write-once, twice over**: the declaration row's reference by the conditional `UPDATE` above, and its detail (who filed it, when ICS2 accepted it) by `BlobEnsDeclarationStore.SaveAsync`, which creates `declarations/{declarationId}.json` with `IfNoneMatch = ETag.All`. `IEnsDeclarationStore` is keyed by declaration id and has no supersede: **withdrawing keeps the row and its blob** (`WithdrawAsync` goes `Accepted → Stale → Withdrawn` in one transaction), so the old MRN stays as history and the replacement is a new declaration with a new id — invalidate-and-refile being the normal correction because several ENS fields are non-amendable. The record is DB-first: a failure between the row and the blob leaves an `Accepted` ENS with no detail, which reads back as 404 on the detail but still satisfies the ELO check. **`GET .../declarations/ens/filing-sheet` is deliberately incomplete**: it composes everything a filer needs *except* the consignee's address, names the consignee at organisation and region only, sets `consigneeAddressWithheld` and says (`consigneeAddressSource`) that the **Ground Officer enters the address in the portal** ([O32](docs/domain/decisions.md#o32)) — so the address never enters a Freedom queue, blob or payload, and never reaches a Dispatcher. It resolves the vehicle's manifest for its cargo, so a vehicle with none has no sheet (404). It also reports its own gaps in `missing` (an unclassified item by name, a route stop with no ISO code, a ferry with no vessel IMO, unvalidated boxes making the gross mass provisional). `dbo.Convoy.CrossingMode`/`VesselImo` exist for this — mode of transport describes the **crossing**, not the vehicle: ferry → 1 maritime, LeShuttle → 3 road, and rail is refused at the Smart Border. The ENS MRN deliberately does **not** go on the GMR: GVMS wants it in `sAndSMasterRefNum`, which hangs off a declaration container whose required primary identifier (a CDS DUCR, a TIR or ATA carnet) Freedom does not hold. `docs/adr/0003-ens-declaration-recorded-not-submitted.md`, `docs/schemas/ics2/onboarding.md` and `docs/gotchas-and-open-questions.md` §5b.

**Boxes are replaced, and the label lists the contents ([ADR 0011](docs/adr/0011-attested-boxes-are-replaced-not-edited.md), plan 16).** `DELETE /boxes/{id}` is `409` for a validated box. `POST /boxes/{id}/replace` (`boxes:write`) runs `BoxRepository.ReplaceAsync` in **one transaction**: it voids the box (conditional on `ValidatedAt IS NOT NULL AND VoidedAt IS NULL`, so the database settles a race), revokes its active QR code, inserts an unattested box with `ReplacesBoxId`, copies the items (category, quantity, value, donor, expiry), vacates its bay and moves its `dbo.ConvoyVehicleBoxAllocation` row to the new box. Refused `409` for a box nobody has validated (`box-not-attested`), one already voided (`box-voided`) and, until plan 15, one whose vehicle's GMR exists (`load-frozen`). A voided box takes no label and no allocation, and **every sum over boxes says `VoidedAt IS NULL`** (manifest lines, ENS goods lines, donor report, receiver usage, cargo list) because the replacement carries the same items and the same donation. The label renderer takes `BoxLabelContent` (`Application/Boxes/BoxLabelContent.cs`): lines of category in English and Ukrainian, quantity and expiry, plus a signer by `SignerCode` (a one-way hash of the `PersonId`, derived and never stored) and first name with last initial from `PersonDisplay`-style erased-volunteer handling ("Former volunteer"). **It must never take a box or item read model**: that type has no description, property, value, donor or receiver, and that is what keeps them off a label that crosses borders (`docs/security/0011-label-review.md`; owner flagged it for revisit, `Q-label-renderer-type`). The Ukrainian name is the category's `NameUk`, Administrator-edited, with the English name standing in when empty. **No machine translation is built or chosen** (`docs/spikes/0011-offline-translation.md`, `Q-label-translation`): there is no Microsoft built-in offline option, and an in-process OPUS-MT model got about half of short item names wrong. The fixed Ukrainian wording on the label was written without a translator.

**Three write-once records, all enforced the same way.** `Convoy.TruckListPublishedAt`, `Box.ValidatedAt`/`ValidatedByPersonId` and `Manifest.Status`/`GmrSubmittedAt` are stamped by a dedicated `POST` transition and are *absent from the corresponding `UPDATE` statement and request body*, so no ordinary edit can set, clear or forge them. Each transition's SQL is conditional (`WHERE ... AND TruckListPublishedAt IS NULL` / `AND ValidatedAt IS NULL` / `AND Status = @from`), so the database settles a race rather than a read-then-write in C#. (`Vehicle.InspectionStatus`/`InspectionNotes` follow the same shape without being write-once: only `PUT /vehicles/{vin}/inspection` writes them, and joining a truck list is conditional on `InspectionStatus = Passed`. `ConvoyVehicle.WithdrawnAt` is a fourth, stamped by `DELETE /convoys/{id}/vehicles/{vin}` once the list is published and conditional on `WithdrawnAt IS NULL`.) Both then freeze their aggregate: a published truck list will not take a new vehicle — though one that breaks down may still be *withdrawn*, which keeps the entry — and a validated box will not take or release an item or change receiver — and a frozen manifest will not be edited — in each case because a manifest or a border document would otherwise be describing something that is no longer true.

**Data sensitivity — read before touching `Receiver`, `Address` or manifest generation.** Ukrainian delivery addresses and receiver contacts are the highest-risk data in the system: a manifest listing precise addresses is a targeting document, and it crosses several borders where it may be inspected or seized. The design segregates that data behind the Ground Officer role, redacts it from anything that travels, and audits every read. Do not widen access to it, add it to a printed document, or log it, without checking with the user first. See `docs/domain/key-concepts.md` § Data Sensitivity.
